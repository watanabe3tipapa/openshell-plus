Critical 深刻な問題

コンテンツの途中欠落

Critical

GitHub Pages の「ガイドの訂正点（実 API との差分）」セクションが途中で強制切断されており、最後の行が get / list / delete / exec は name と workspa... で終わっている。読者に対して重要な実装注意点が不完全な状態で公開されている。

推奨対応: 該当セクションの全文を確認し、欠落部分を補完する。同様に、他のセクションでも末尾の切れがないか一括検証すること。

WebSocket 認証で URL クエリパラメータによるトークン受付

Critical

README によれば、WebSocket はブラウザからヘッダを付けられないため Sec-WebSocket-Protocol: bearer.* と ?token= の両方を受理している。URL クエリに認証トークンを含める設計は、サーバーアクセスログ・ブラウザ履歴・リファラーにトークンが残るリスクがある。

推奨対応: ?token= による受付を廃止し、WebSocket 接続確立前の別途 HTTP エンドポイントで一時的な接続 ID（JWT 等）を発行してから WebSocket へ移行する方式、または Subprotocol 方式のみに絞ることを検討。どうしても必な場合は、そのリスクをドキュメントに明記し、トークンの有効期限を極力短く設定すること。

High 重要な改善事項

1 ページへの情報過多とナビゲーション不足

High

GitHub Pages は単一ページに OpenShell 本体の解説、脅威モデル、構成要素、ネットワーク要求の流れ、デプロイ形態、Colab 手順、環境変数一覧などが全て詰め込まれている。スクロール量が極端に多く、目的の情報に到達するまでの導線が弱い。目次（TOC）やページ内検索もない。

推奨対応: ランディングページは「openshell-plus とは何か・何ができるか・始め方」の 3 要素に絞り、詳細な技術解説は別ページ（Getting Started / Reference / Security 等）へ分割。固定ヘッダーまたはサイドバーでグローバルナビゲーションを提供すること。

スクリーンショット・デモ動画の欠如

High

UI/UX ダッシュボード製品であるにもかかわらず、README および GitHub Pages に実際の画面キャプチャや短いデモ GIF が存在しない。Stars/Forks が 0 である背景には、視には、視覚的な価値訴求が弱いことが大きく影響している可能性がある。

推奨対応: 以下を作成・掲載すること。
  • ダッシュボードの主要画面（一覧 / コンソール / 作成フォーム）のスクリーンショット
  • 10〜15 秒程度の操作デモ GIF または動画（sandbox 作成からコマンド実行まで）
  • OGP 画像（ソシャルシェア時のプレビュー用）

demo フォールバックのデフォルト有効化リスク

High

デフォルトで gateway 接続失敗時に demo backend へフォールバックする。ローカル開発では便利だが、本番運用時に意図せず demo モードで起動し、ユーザーが実際の sandbox 操作を行っているつもりでモックデータを操作する事故が起こりうる。

推奨対応: 本番環境（OSUI_MODE=cloudflare / vercel / colab 以外の公開 bind）では、起動時に demo フォールバックを無効にするか、UI に常時「DEMO MODE」バナーを表示して視覚的に区別すること。あるいは OSUI_REQUIRE_GATEWAY をデフォルト true に変更し、明示的なオプトインで demo を有効化する設計を検討。

プロジェクト運用基盤の未整備

High

リポジトリに CONTRIBUTING.md、CHANGELOG、GitHub Releases、Issue テンプレートが存在しない。外部からのフィードバックや協力を受ける仕組みがなく、プロジェクトの持続可能性が低い。

推奨対応:
  • CONTRIBUTING.md（開発環境築、PR フロー、コミット規約）
  • CHANGELOG.md（Semantic Versioning 準拠）
  • GitHub Issue / PR テンプレート
  • 初回の GitHub Release（v0.1.0 等）を作成し、変更概要を記載

英語版の存在が不明確

High

README に「日本語 | English」とあるが、English 版へのリンク先や実際のコンテンツが確認できない。NVIDIA OpenShell はグローバルなプロジェクトであるため英語ドキュメントの有無は採用率に直結する。

推奨対応: 英語版ページ（/en/ 等）を作成するか、現時点で未対応なら「英語版は準備中」と明記。README のリンクを切れない状態に保つこと。

Medium 中程度の改善事項

SEO / OGP / アクセシビリティの未確認

Medium

GitHub Pages のメタタグ（description, og:title, og:image, twitter:card 等）や構造化データの有無が不明。検索エンジンや SNS からの流入を最大化するための基盤が整っているか確認が必要。また、カラーコントラスト、キーボードナビゲーション、スクリーンリーダー対応（aria-label 等）の検証も推奨される。

推奨対応: Lighthouse（Chrome DevTools）でスコアを計測し、SEO / Accessibility / Best Practices が 90 以上を目標に改修。特に OGP 画像と正確な meta description を設定すること。

エラーハンドリングとユーザーへのフィードバック設計

Medium

ドキュメント上、エラー時の UI 挙動（例: gateway 接続タイムアウト、policy 違反、認証失敗時のメッセージ）の記述が少ない。ユーザーがトラブルに遭遇した際に原因を自己解決できる設計になっているか不透明。

推奨対応: 主要なエラーコード・例外を一覧化し、UI 上に「原因 / 対処法」を提示するヘルプリンクを設置。トースト通知やインラインエラーメッセージのデザインパターンを統一すること。

テスト・カバレッジの可視化

Medium

uv run pytest でテスト実行は可能とあるが、テストカバレッジの基準や CI 上での自動計測（Codecov 等）の有無が不明。信頼性の高い OSS としてはカバレッジレポートの公開が望ましい

推奨対応: GitHub Actions で PR 時に pytest + coverage を実行し、カバレッジバッジを README に掲載。目標カバレッジ（例: 70% 以上）を CONTRIBUTING.md に明記すること。

インタラクティブ構成図のフォールバック

Medium

「インタラクティブに操作できる構成図」と謳っているが、JavaScript 無効環境や一部のモバイルブラウザ、RSS リーダー内では表示されない可能性がある。

推奨対応: 静的な PNG / SVG 版の構成図を <noscript> または画像要素で並設し、検索エンジンや代替環境でも情報が伝わるようにすること。

Low 軽微な改善・最適化

README の「Version」表記が空欄

Low

README 内に「Version」とあるが値が記載されていない。細部の見栄えに影響。

推奨対応: 現在のバージョン（例: 0.1.0）を記入し、リリース時に更新する運用を徹底。または動的バッジ（shields.io）を利用。

ファビコン・ブランドカラーの未設定

Low

独自のファビコンやテーマカラー（theme-color）が設定されていない場合、ブラウザタブやモバイルホーム画面での印象が弱い。

推奨対応: openshell-plus 独自のロゴマーク（シンプルなアイコンでも可）を作成し、ファビコンと Apple touch icon、theme-color メタタグを設定すること。

pip ベースの代替インストール手順

Low

uv を推奨しているが、従来の pip ユーザーや Poetry ユーザーのための代替手順がない。導入障壁を下げる観点から補足が望ましい。

推奨対応: README に「uv を使わない場合」の最小手順（requirements.txt 等）を追記、または pip install -e ".[dev]" 相当のコマンド例を提示すること。

評価できる点

  • セキュリティ設計明示: loopback 以外 bind 時のトークン強制、demo フォールバックの切り替え、mTLS / OIDC 対応など、公開安全性を意識した設計がコード・ドキュメント双方に反映されている。
  • lint / 型チェックの整備: ruff と pyright を併用しており、コード品質の基盤は良好。
  • 多様なデプロイ形態: ローカル・Cloudflare・Vercel・Colab の 4 形態を同一コードベースでカバーする設計は実用的で評価できる。
  • ドキュメント訂正の取り組み: OpenShell 公式ガイドと実 SDK の差分を整理し、実装に反映している点はユーザー視点で価値が高い。
